Tu proyecto, en un repo que no se olvida

El harness junta reuniones, mails, canales y tareas de tu proyecto en un repositorio git privado de la org. Claude lo lee antes de trabajar, así que no arrancás de cero cada sesión. Y si mañana entra alguien nuevo, clona el repo y sigue desde donde quedaste.

Esta guía la recorrés sobre un proyecto real en el que estés trabajando. Al terminar tenés:

Memoria del proyectoOverview, reuniones resumidas y preguntas abiertas.
Bitácora de decisionesQué se decidió, por qué y con qué fuente.
Diagrama de arquitecturaCódigo + PNG con íconos oficiales de AWS.
Backlog y dailyTus tareas priorizadas y tu reporte para la daily.
Una skill propiaTu tarea repetitiva, automatizada.
El modelo

Cómo fluye el conocimiento

Las fuentes entran por los conectores de claude.ai. Las skills las resumen y las guardan como archivos chicos en el repo del proyecto. De ahí salen el status, la daily, los diagramas y las tareas.

Para todos · ~2 h la primera vez

Recorrido común

Estos ocho pasos son iguales para Data, AI y ML. Después seguís con los ejercicios de tu rol.

  1. Instalá el harness

    Clonalo en ~/claude-workspace. Las skills asumen esa ruta.

    terminal
    git clone https://github.com/JuanMartinezDinoCloud/claude-harness.git ~/claude-workspace
cd ~/claude-workspace
    Windows (PowerShell)
    powershell -ExecutionPolicy Bypass -File harness\install.ps1
# diagnóstico
powershell -ExecutionPolicy Bypass -File harness\install.ps1 -Status
    macOS
    bash harness/install.sh --all
# diagnóstico
bash harness/install.sh --status

    Después configurá tu usuario. role = "engineer" hace que la ingesta, el status y la daily muestren lo tuyo y no todo el equipo.

    terminal
    cp harness/config.example.toml harness/config.toml
    harness/config.toml
    [user]
name = "Tu Nombre"
email = "tu.usuario@dinocloud.com"
role = "engineer"          # "engineer" | "tl-sa"
slack_user_id = "U0XXXXXXX" # tu propio ID: el DM de las rutinas te llega a vos

    Por último, en claude.ai → Settings → Connectors, autenticá Google Calendar, Gmail, Google Drive, Slack, ClickUp y GitHub. Abrí claude en la terminal y corré /skills: tenés que ver project-new, project-ingest, backlog, aws-diagram y el resto.

  2. Dá de alta tu proyecto real

    project-new te pide el cliente y el alcance autorizado, crea la estructura, busca las fuentes con los conectores y deja el repo privado en la org dinocloud.

    prompt en Claude Code
    Dá de alta el proyecto <tu-proyecto> en el harness. Soy <Data Engineer | AI Engineer | ML Engineer>. El canal interno de Slack es <#canal> y las reuniones tienen "<palabra del título>" en el nombre.
    ANTES DE TRAER MATERIAL DEL CLIENTE
    Confirmá el nombre del cliente y el alcance autorizado. Mientras scope_confirmed = false, el harness solo procesa fuentes internas. El repo del proyecto siempre es privado en la org, nunca en tu cuenta personal.

    Al final, project-new te propone crear el remoto y lo corre con tu OK:

    lo propone project-new
    gh repo create dinocloud/<tu-proyecto>-harness --private --source . --push

  3. Poblá el conocimiento con tus reuniones

    Traé las últimas 2 o 3 semanas. En modo ingeniero entran las reuniones en las que participaste y tus hilos de Slack y Gmail. De cada reunión se lee la nota de Gemini; el transcript no se copia.

    prompt
    Ponete al día con <tu-proyecto>: ingerí las reuniones y canales de las últimas 3 semanas.

    Después revisá lo que quedó: docs/00-overview.md, docs/decisions/decisions.md y memory/open-questions.md. Corregí lo que esté mal: es tu memoria.

    prompt
    Mostrame las decisiones y las preguntas abiertas que salieron de la ingesta. ¿Qué reuniones quedaron sin notas?

  4. Armá el diagrama de arquitectura

    aws-diagram escribe el diagrama como código Python (librería diagrams) con los íconos oficiales de AWS y genera PNG y SVG. Primero lee el Terraform, CDK o código del repo: no dibuja lo que supone.

    una sola vez
    bash ~/.claude/skills/aws-diagram/setup.sh
# en Windows instala graphviz con winget; después: setup.sh --check
    prompt
    Leé el Terraform de <ruta-al-repo-de-infra> y armá el diagrama de arquitectura de <tu-proyecto> en docs/diagrams/. Marcalo como confidencial.
    CHEQUEO OBLIGATORIO
    Antes de pegarlo en un doc: sin account IDs, ARNs, IPs reales, nombres de buckets productivos ni marca del cliente. La skill corre el grep y te muestra los hits.

  5. Generá tu daily report

    En modo ingeniero la daily es una tarjeta tuya: qué hiciste ayer (commits, tareas movidas en ClickUp, decisiones), qué hacés hoy y qué te bloquea. Sale en HTML y en texto para pegar.

    prompt
    Armá mi daily report de <tu-proyecto> para mañana.

  6. Registrá una decisión técnica tuya

    Cada decisión lleva contexto, qué se decidió, consecuencias, estado y la fuente. Lo descartado queda acá, no en el documento de diseño.

    prompt
    Registrá en la bitácora la decisión de <qué decidiste>. Contexto: <por qué surgió>. Alternativas descartadas: <cuáles y por qué>. Fuente: <link a reunión, PR o hilo>.

  7. Convertí una tarea repetitiva en skill

    La regla: la hacés una vez a mano; si la pedís por tercera vez, pedile a Claude que la convierta en skill. La mejora queda anotada en harness/improvements.md y harness-evolve sigue proponiendo otras cada semana.

    prompt
    Esto de <tarea que repetís> ya lo hicimos varias veces. Creá una skill del harness para hacerlo, probala en un proyecto de prueba y anotala en improvements.md.

  8. Subí todo: eso es la KT

    Las skills commitean solas con mensajes harness(<skill>): …. Vos hacés el push al cerrar el día. Quien entre al proyecto clona el repo, abre Claude Code adentro y pregunta.

    terminal
    cd ~/dino-projects/<tu-proyecto> && git push
La memoria del porqué

Bitácora de decisiones

El código dice qué se hizo; la bitácora dice por qué. Cada decisión técnica o de producto queda registrada con su contexto, la alternativa que ganó, lo que implica y de dónde salió. Vive en docs/decisions/decisions.md, dentro del repo del proyecto.

No se vuelve a discutir"¿Por qué no usamos X?" tiene respuesta con fecha y fuente, no depende de la memoria de nadie.
La KT sale solaQuien entra al proyecto lee las decisiones vigentes y entiende la solución sin una reunión de 2 horas.
Claude decide mejorAntes de proponer algo, Claude lee la bitácora: no te sugiere lo que ya se descartó ni contradice lo acordado.
Respaldo ante el clienteSi alguien pregunta quién y cuándo acordó un cambio de alcance o de arquitectura, está el link a la reunión o al hilo.

D-007 — Carga incremental con CDC en lugar de carga completa diaria

Fecha
2026-10-06 · decidió el equipo de datos con el owner técnico · fuente: link a la reunión de arquitectura
Contexto
La carga completa tarda 3 h y no llega antes de las 07:00 cuando crece el volumen.
Decisión
Captura de cambios (CDC) sobre las 4 tablas más grandes; el resto sigue con carga completa.
Descartado
Escalar el cluster: resuelve el horario pero duplica el costo mensual.
Consecuencias
Hay que monitorear el lag de replicación; el reproceso histórico pasa a ser un job aparte.
Estado
vigente

Reglas

  • Una decisión por entrada, con fuente siempre: reunión, hilo, PR o mail.
  • Lo descartado va en la decisión, no en el documento de diseño: el diseño muestra solo el estado final.
  • Nada se borra. Si cambia, se registra una nueva y la anterior queda reemplazada por D-NNN.
  • Se busca por id o palabra clave en index.toon; no hace falta leerla entera.
  • Cuando crece mucho, project-consolidate mueve las reemplazadas a un archivo histórico.
registrar
Registrá en la bitácora: decidimos <qué> porque <por qué>. Descartamos <alternativa>. Fuente: <link>.
consultar
¿Por qué decidimos <tema>? Citá la decisión y su fuente.
revisar la semana
¿Qué decisiones se tomaron o cambiaron esta semana?
reemplazar
Cambiamos de idea sobre <tema>: registrá la nueva decisión y marcá la anterior como reemplazada.
OJO
Los ids D-NNN son internos del repo. En un ticket, un mail o un mensaje al cliente, la decisión se explica en palabras.
Tus tareas

Backlog interno

ClickUp es la verdad de lo que ejecuta el equipo. El backlog interno es la verdad de tus tareas: lo que anotás al vuelo, lo que sale de una reunión y todavía no es ticket, lo que preparás antes de subir. Vive en dos archivos: backlog/backlog.toon (la tabla) y backlog/notes.md (el detalle de cada tarea).

backlog/backlog.toon · ejemplo
backlog[3]{id,title,status,priority,due,blocks,owner,phase,clickup_id,updated}:
  T-001,Garantizar frescura diaria de la tabla de ventas,doing,P1,2026-10-15,T-003,yo,F2,,2026-10-08
  T-002,Documentar el linaje de las tablas de clientes,todo,P3,,,yo,F2,,2026-10-07
  T-003,Exponer métricas de ventas al tablero comercial,todo,P2,2026-10-22,,yo,F2,,2026-10-08

T-001 — Garantizar frescura diaria de la tabla de ventas

Objetivo
La tabla de ventas tiene los datos del día anterior antes de las 07:00.
Por qué
El tablero comercial la usa a primera hora; hoy llega tarde 2 de cada 5 días.
Criterios
  • 10 días hábiles seguidos con carga antes de las 07:00
  • Alerta en el canal si a las 07:00 no hay datos
Restricciones
Sin aumentar el costo mensual del pipeline más de 10 %.
Entregable
PR mergeado + runbook en docs/.

La regla de prioridad es la misma para todo: primero lo que bloquea a otra persona, después lo que tiene fecha, después el camino crítico. P1 a P4.

agregar
Anotá una tarea en el backlog de <tu-proyecto>: <qué hay que lograr y por qué>.
propuestas de la ingesta
Mostrame las propuestas de backlog pendientes y vamos una por una.
priorizar y listar
Repriorizá mi backlog y mostrame solo lo que cambió.
subir a ClickUp
Subí T-003 a ClickUp. Mostrame el contenido antes de crearla.

Avanzado · una vez por persona

API de Google: Drive, Docs y Sheets

Los conectores de claude.ai leen bien. Para editar un Google Doc o un .docx en Drive, subir un archivo, o leer una planilla en una rutina desatendida, hace falta la API directa con tu propio token OAuth.

  1. Tu proyecto de Google Cloud

    Creá un proyecto nuevo en console.cloud.google.com con tu cuenta @dinocloud.com (por ejemplo, claude-harness-<tu-nombre>). No hace falta pedirle nada a nadie. Después, en APIs y servicios → Biblioteca, habilitá Google Drive API, Google Docs API y Google Sheets API.

  2. Pantalla de consentimiento Internal

    Tipo Internal: solo entran cuentas @dinocloud.com y los tokens no vencen a los 7 días como en modo Testing.

  3. Credencial OAuth de tipo Desktop app

    Credentials → Create credentials → OAuth client ID → Desktop app → Download JSON. Guardalo así:

    terminal
    mkdir -p ~/.config/claude-harness
mv ~/Downloads/client_secret_*.json ~/.config/claude-harness/google-client.json

  4. Dependencias en el venv del harness

    El instalador ya creó harness/.venv con harness/requirements.txt (google-auth, google-auth-oauthlib, google-api-python-client, desde PyPI). Si te lo salteaste:

    Windows (PowerShell)
    powershell -ExecutionPolicy Bypass -File harness\install.ps1
    macOS
    bash harness/install.sh --python

  5. Primer login

    terminal
    # Windows
harness\.venv\Scripts\python.exe harness\scripts\google-login.py --scopes drive.readonly documents drive.file
# macOS
harness/.venv/bin/python harness/scripts/google-login.py --scopes drive.readonly documents drive.file

    Se abre el navegador, aceptás y queda un token en ~/.config/claude-harness/token-<scopes>.json. Con esos tres scopes leés Drive, editás Docs y subís archivos nuevos. Si después necesitás otro, repetís el login con el scope que falta.

  6. Elegí el scope mínimo

    ScopePara qué
    drive.readonlyLeer Docs y archivos de Drive.
    documents.readonly · documentsLeer o editar el contenido de un Google Doc.
    spreadsheets.readonly · spreadsheetsLeer o editar planillas.
    drive.fileCrear y editar solo los archivos que crea el harness, por ejemplo subir un diagrama.
    driveEditar documentos existentes de otros. Pedilo solo si de verdad lo necesitás.

  7. Probalo desde Claude

    leer
    Leé el Google Doc <link> y resumilo en 5 viñetas.
    editar · te muestra el diff y pide OK
    En el doc <link>, reemplazá "<texto viejo>" por "<texto nuevo>". Primero en dry-run.
    subir
    Subí docs/diagrams/<diagrama>.png a la carpeta de Drive del proyecto.
    planilla
    Traé el rango A1:F50 de la hoja "<hoja>" de <link> y decime qué filas cambiaron desde la semana pasada.

    Claude elige la skill google-api sola. Si querés ver qué corre por debajo:

    referencia · PY = harness/.venv/Scripts/python.exe (Windows) o harness/.venv/bin/python (macOS)
    GAPI=~/claude-workspace/harness/skills/google-api/gapi.py
$PY $GAPI ls <folder_id>
$PY $GAPI read <file_id> --out doc.md               # Doc → Markdown, Sheet → CSV
$PY $GAPI sheet <id> --range "Hoja!A1:F50"
$PY $GAPI replace <doc_id> --find "X" --replace "Y"  # dry-run
$PY $GAPI replace <doc_id> --find "X" --replace "Y" --apply
$PY $GAPI upload archivo.png --folder <folder_id>    # drive.file
$PY $GAPI upload archivo.png --update <file_id>      # drive
SíntomaCausa y arreglo
access_deniedConsent en modo External o entraste con una cuenta fuera de dinocloud.com.
invalid_grant o token vencidoBorrá ~/.config/claude-harness/token-<scope>.json y repetí el login.

404 en un archivo del clienteNo te lo compartieron. Pedí acceso; no lo copies a tu Drive.
REGLAS
Toda escritura en Drive va con tu OK explícito. Los archivos del cliente se leen solo si el alcance está autorizado. Nada de PII en logs ni en el repo.
Cómo trabajamos

Buenas prácticas

Sí

  • Usá Claude Code en la terminal: ves y controlás el contexto con /context, /compact y /clear.
  • Abrí la sesión dentro del repo del proyecto (~/dino-projects/<proyecto>): el CLAUDE.md le dice qué leer primero. Para tocar el harness, en ~/claude-workspace.
  • Lo del proyecto va al repo (decisions.md, CLAUDE.md, status/); la auto memory de Claude, solo para tus preferencias de trabajo.
  • OK explícito antes de escribir afuera: ClickUp, Drive, mails, Slack a otros.
  • Markdown para prosa, .toon para tablas. Fechas AAAA-MM-DD.
  • Commits chicos y PRs atómicas. Push al cerrar el día.
  • Si corregís algo dos veces, pedí que quede como regla o como mejora en improvements.md.

No

  • Credenciales en archivos, prompts o diagramas. Van en variables de entorno o Secrets Manager.
  • Transcripts ni mails copiados enteros: solo resumen, decisiones y link.
  • IDs internos (T-, D-) o rutas locales en texto que sale del repo, como un ticket o un mail.
  • Material del cliente sin confirmar el alcance autorizado.
  • Repos de proyecto en tu cuenta personal de GitHub.
  • Abrir Claude en tu home para trabajar un proyecto: lo que aprende queda en una memoria local, fuera del repo y de la KT, y se mezcla con otros clientes.
Autoevaluación

¿Cómo sé que lo estoy usando bien?

  • El 00-overview.md entra en una pantalla y alguien nuevo entiende el proyecto leyéndolo.
  • Cada decisión de la bitácora tiene fuente: reunión, PR o hilo.
  • Tu daily sale del harness y no la escribís a mano.
  • Tu backlog está priorizado y no tiene tareas que ya existen en ClickUp.
  • El diagrama está en docs/diagrams/ como .py + .png y coincide con el IaC.
  • Creaste al menos una skill propia y tenés una mejora anotada en improvements.md.
  • Si mañana te vas de vacaciones, quien te cubre clona el repo y sigue.
